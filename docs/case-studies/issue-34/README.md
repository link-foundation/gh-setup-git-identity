# Issue #34 case study — a signed-in GitHub CLI account lacked email access

The application treated a successful `gh auth status` as proof that it could fetch the authenticated user's primary email. The reported credential passed that check, then GitHub rejected `GET /user/emails` and `gh` identified a missing OAuth scope. Signing in again with `user` restored the lookup. The fix starts the existing login flow once on the permission error and fetches the username and email again before writing Git identity. [Issue #34](https://github.com/link-foundation/gh-setup-git-identity/issues/34) · [Reported terminal transcript](raw-logs/issue-report.txt)

## Root causes and affected entry points

1. **The preflight checks authentication, while the failed operation checks email permission.** The CLI only initiated login on a nonzero `gh auth status`. The library treated any `gh api user/emails` failure as an ordinary setup error, so the CLI exited even when `gh` described a recoverable scope issue. GitHub documents `user:email` for classic token email reads. The parent `user` scope includes it. Fine-grained user tokens need the read permission for email addresses. The live API advertises `user, user:email` in its accepted OAuth scopes header. [REST email endpoint](https://docs.github.com/en/rest/users/emails#list-email-addresses-for-the-authenticated-user) · [OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) · [Captured response headers](raw-logs/email-endpoint-headers.txt)
2. **A host or account can change across authentication.** The old CLI supplied `--hostname` for login and credential helper setup, while status and identity requests let `gh` choose their host. Restarting only the failed email call could also pair the old username with a newly authorized email. The CLI now passes its selected host through every setup operation and looks up both fields again after login. The recovery path waits for the original lookups to finish before replacing the active credential.
3. **The upstream scope hint lacks credential-source context.** `gh api` derives the scope hint from the error status and OAuth response headers. The hint recommends refreshing stored credentials even when an environment variable supplies the active token. `gh auth refresh` explicitly rejects that source. The loopback test reproduces this secondary problem independently of the reporter's unknown credential source. The application now names the applicable variable and explains how to provide a usable token. [Scope suggestion code](https://github.com/cli/cli/blob/v2.105.0/api/client.go#L342-L411) · [Refresh command](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/auth/refresh/refresh.go#L191-L195) · [Upstream issue](https://github.com/cli/cli/issues/15129)
4. **The opt-out flag was declared in the wrong form for the argument parser.** Yargs parses `--no-auto-login` as `auto-login=false`. Strict mode rejected the flag when the positive form was undefined, and the old test only scanned source text. The CLI now declares `auto-login` and tests the user-facing negated flag against both signed-out and insufficient-scope credentials.

The CLI recognizes the `user` and `user:email` hints and explicit token-access denials from the email endpoint. A bare HTTP 404, a missing primary email, and failures from the username lookup still surface as setup errors. Low-level lookup functions perform only reads. Library consumers of `setupGitIdentity` can enable the same one-attempt recovery by passing `authOptions`.

## Options considered

| Approach | Fit for this incident |
| --- | --- |
| Reuse `gh auth login`, then rerun the identity lookup | Matches the successful workaround, delegates device authorization and secure storage to `gh`, and allows the user to choose or reauthorize an account. The implementation preserves login flags and adds a necessary OAuth scope for custom lists that omit email access. |
| Run `gh auth refresh -s user:email` | A manual option for the active stored account when preserving that account is desired. It cannot select a different account or update an environment-provided token. [GitHub CLI refresh manual](https://cli.github.com/manual/gh_auth_refresh) |
| Switch an already-authorized account with `gh auth switch` | Useful when the user already knows which stored account has the needed permission. The application cannot infer a preferred account from the permission error. [GitHub CLI switch manual](https://cli.github.com/manual/gh_auth_switch) |
| Use a user token supplied by the caller | Fits automation and the existing `--with-token` interface. Environment token precedence is controlled by `gh`. Recovery tells the caller how to remove or replace an environment credential that lacks email access. [GitHub CLI environment manual](https://cli.github.com/manual/gh_help_environment) |
| Replace `gh` API calls with Octokit and implement device authorization in JavaScript | Octokit can perform the REST request and device authorization. The application would also need to manage GitHub CLI's active account and credential store so later `gh` and Git commands use the same identity. [Octokit device authorization](https://github.com/octokit/auth-oauth-device.js) |
| Use the public profile email or synthesize a noreply address | An identity fallback could be useful for other tooling. This tool promises the account's primary email, which may be private and different from either value. Native Git identity setup has been proposed separately. [cli/cli#6096](https://github.com/cli/cli/issues/6096) |
